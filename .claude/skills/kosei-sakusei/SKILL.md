# 構成作成スキル（kosei-sakusei）

**正本**：本ディレクトリの [要件定義.md](要件定義.md)（構成ロジック・品質基準の全定義）。本SKILL.mdは実行手順の入口で、詳細は §番号で 要件定義.md を参照する。実記事の傾向は [reference-yamadai-outlines.md](reference-yamadai-outlines.md)。
**大原則**：構成は固定テンプレ／型で決めない。毎回「競合上位の構成（§5.2・§6.3）＋依頼情報（KW・訴求順位・掲載サービス・その他指示）」で組む（§6）。過去記事の並びは参考実例であって固定ルールではない。

---

## 使うとき
- ヤマダイ（super-yamadai.co.jp/article）の新規/リライト記事の構成案を作るとき。
- 入力：**ターゲットKW ＋ 依頼情報（依頼シート）**。依頼情報がなくKWだけのときは Phase 0 で自動リサーチする。

## 🚨 絶対に守る（レビュー最頻の指摘・§7冒頭）
1. **1つのH2（配下H3まで含めて）で1トピック。** 「〜と〜」「〜や〜」で2トピックを並べない（要るなら別H2に割る）。
2. **一読で意味が取れない見出しを作らない。** 「980円の違い」等の圧縮語NG。何がどうなのか具体語で。
3. **競合の焼き直し・全部盛りにしない。** 記事の主役（ペルソナの最大不安／検索意図の核）を1つ決めて尖らせる。網羅は手段で目的ではない。
4. **見出しは結論・平易（中学生が一読）・カッコ/記号なし。** お手本（[references/gold-example-style.md](../../../references/gold-example-style.md)・[structure-examples.md](../../../references/structure-examples.md)）に文言を寄せる（丸パクリ禁止）。
5. **推測で数値・事実を書かない。** 裏取りできないものは書かず末尾免責へ（§F-4/§E-11）。
6. **H2・H3は答え・結論を書く**（目次だけで結論がわかる。箱だけの見出し＝「料金の目安」「中身と種類」等は全否認）。セクション名はSEO標準語（注意点/デメリット/メリット/選び方/口コミ/評判 等）を優先。FAQ質問H3のみ例外。
7. **FAQは4〜6問（できれば6問）。** 本文未回収のPAA・サジェストから。

## 手順

### Phase 0: 自動リサーチ（KWだけ渡されたとき・§2/§5.2）
ターゲットKWから依頼シートの各欄を可能な範囲で自動取得する。Ahrefs MCP は初回 `doc` で使い方を確認してから該当ツールを呼ぶ。取得できない欄は「未取得・要手動」と明示する（沈黙で埋めない・§2.5）。

| 依頼欄 | 取得元（MCPツール） |
|---|---|
| 検索ボリューム・難易度 | Ahrefs `keywords-explorer-overview` |
| サジェスト・複合KW | Ahrefs `keywords-explorer-search-suggestions` ＋ `keywords-explorer-matching-terms` |
| 関連KW | Ahrefs `keywords-explorer-related-terms` |
| 競合上位URL（SERP） | Ahrefs `serp-overview` → 上位URLを WebFetch して H2/H3 抽出・クラスタリング |
| 自サイトのカニバリ・順位 | **Windsor.ai `searchconsole` コネクタ**（get_fields→get_data で自サイトのクエリ×ページ×掲載順位）＋ internal-links.md 照合。※super-yamadaiのGSCは要接続（onboard.windsor.ai → searchconsole）。未接続時は Ahrefs `site-explorer-organic-keywords`（自ドメイン）で代替 |
| 行動データ（ページ流入） | **Windsor.ai `googleanalytics4` コネクタ**（ヤマダイ接続済み・プロパティ 528283108 / 528278970。page_path×screen_page_views×sessions 等） |

- **自動取得しにくい欄はLLMで補完**（捏造禁止）：PAA（SERPのPeople Also Ask）／共起語（競合本文から頻出語抽出）／ペルソナ・ニーズ・知恵袋層（SERP＋一次情報の読み取りで仮説化し、断定しない）。
- 依頼シートが渡された場合は Phase 0 をスキップし、その内容を最優先で使う（数値・順位は1:1で扱い勝手に変えない）。

### Phase 1: モード判定（§4）
既存記事の有無＋順位資産で A リライト / B リポジショニング / C 新規 を判定。曖昧・順位取得不能なら聞き返す。

### Phase 2: SERP適合＋重複/カニバリ（§5.1G・§5.2）
- 実SERPの記事タイプ（比較/公式/EC/知恵袋/動画）を判定。狙うタイプが不一致なら構成を作る前に提起。
- 実データ＋SERP同一性でカニバリ判定 → 新規/既存強化/統合/棲み分けの決定木。棲み分け新規なら他社比較はスペック表を作らず向き不向きのみ・内部リンク誘導文も貼らない。
- **着手前に必ず Windsor→GSC で自サイトの既存ランクを確認**（指名/複合クエリで既にどのページが何位に出ているか）。**依頼が「新規」でも既存記事が拾っていればリライト/強化案件**（実例：2026-07「オイシックス お試し」は依頼上「新規」だったが、GSCで既存 #878 が pos3〜10 で存在＝リライト案件と判明。GSCなしでは重複記事を作るところだった）。

### Phase 3: 競合逆算で骨格を出す（§6.3・構成決定の本体）
上位10記事のH2/H3をクラスタリング → 必須トピック＋ギャップ。そこに依頼情報（訴求順位・掲載サービス）を最優先で重ねる。**型テンプレから生成しない。**

### Phase 4: 構成を組む（§6.1）
1. **記事の主役を1つ決める**（ペルソナの最大不安／検索意図の核）。
2. 読者の意思決定順（何がある?→どれ?→使うと?→注意→残る疑問→行動）に並べる。
3. 蛇足・水増しを削る（§5.1D・§7・§9）。
4. 単一サービスのレビュー/ガイド型は「選び方→サービス紹介〇選」テンプレを当てない（§6.3の勘所）。
5. 独自性（一次情報）枠を最低1つ確保（§6.4）。

### Phase 5: 品質ゲート（出力前に必ず1周）
- **論理関係ゲート（§9）**：各H2の"約束"を1文で言語化 → 全H3がその約束に答えるか → MECE・同粒度 → 崩れたら統合/分割/移動/削除で直す。
- **見出し文言（§8＋お手本）**：1H2=1トピック／意味不明なし／結論・平易／カッコ・記号なし／タイトルの数値・訴求をH2で三重掲載しない。
- **H2・H3にメインKWの構成要素＋共起語を左詰めで自然に**（全H2ベタ貼りの機械反復はせず自然分散・§10.2／§F-1）。
- **H2・H3・タイトルに疑問符（？）を使わない**（「〜とは？」等の疑問符フックは平叙の名詞句に）。例外はFAQ質問H3の「〜ですか？」のみ（§A-6）。
- **タイトル/メタ（§10.1）**：記号・年号・感嘆符なし、メインKW左詰め、35〜45字。メタ120〜140字。URL英小文字ハイフン。サブKW2〜4。
- 差別化（上位を何で抜くか）・カニバリ棲み分け・依頼反映（ペルソナ/主要意図/PAA→FAQ/共起語/想定H2数）を再確認。

### 出力（§10）
`articles/{日本語KW}/outline.md` に：タイトル＋メタ＋URLスラッグ＋サブKW／各H2（約束1文付き）＋H3／FAQ（本文未回収のPAAのみ・語尾「〜ですか？」）／カニバリ判定・差別化メモ。リライト時は操作タグ（※既存のまま／→変更／→新規／〔削除〕）と末尾に変更まとめ表。
- リサーチは `articles/{KW}/research.md` に保存する。
- **⚠️ 出力は「ファイル＋チャット要約」を必ずセットで。** リサーチ・構成・分析は、ファイル保存だけで終わらせず、**チャットにも一目でわかる要約（ボリューム・難易度・SERP上位・主要サジェスト・示唆）を必ず出す**。ファイルリンクだけで済ませない（§10）。
- **⚠️ 構成案のチャット表示は H1/H2/H3 の見出し階層だけで見やすく出す**（約束文・差別化/カニバリメモ・要裏取りは見出しツリーの後に分けて添える。構成本体は見出しだけで一目で追えるように）。
- **⚠️ 見出し・見出し行に（　）の注記を付けない**（「（主役）」「（約束：…）」等）。丸カッコ注記はチャットにもファイル見出し行にも付けず、主役/メモは丸カッコなしで別行に（例：★主役＝H2②）。見出し内カッコ禁止（§8-2）をチャット表示にも徹底。

## 第三者レビュー・鵜呑み禁止
- 構成案v1・骨格段階・確定前に `Agent(subagent_type="codex-reviewer", ...)` を呼び、蛇足・重複・カニバリ・論理破綻・過剰一般化を検出（採否は1件ずつ判断）。
- 依頼を「確定」と言われても、ペルソナに刺さらない・蛇足・重複の懸念があれば AskUserQuestion で提起してから着手（§3.7）。

## モデル設定の目安
- 生成・統合・最終化＝opus 高effort。機械的な整形＝低effort。多案比較や網羅が要るときは Workflow（生成→判定→敵対検証→最終化）で回す。
