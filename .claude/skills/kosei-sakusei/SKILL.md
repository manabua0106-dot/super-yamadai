判定を通ったら、次の9つを当てる（1〜8は見出し1本ずつ、9は構成全体に）：

1. **1H2＝1トピック。** 「〜と〜」「〜や〜」で2つ並べたら分割。「向いている人／向いていない人」「良い口コミ／気になる口コミ」のような対概念も同様に別H2。
2. **H2は抽象、H3は具体（2026-10-02 Manabuさん指示・花田の2026-09-30の方式を移植。これから作る構成だけが対象で、公開済みの記事と既存の構成は変えない）。** H2＝「ブランド名＋セクション名」の名詞句だけ（例：〇〇の料金プラン／〇〇の追加費用／〇〇を1か月使ったときの食費／〇〇を安く続ける頼み方）。**H2に答え・結論・金額・条件節（〜すると〜／〜なら〜）を書かない。** 答えはH2直下の「約束：」行とH3に置く。セクション名はSEO標準語（注意点/デメリット/メリット/選び方/口コミ/評判/料金/手順）を優先する。H3＝そのH2の中身を、判断対象を直接書いて言い切る具体（例：14食コースの2回目以降は送料込みで1食約889円）。H3は「別の新しい事実」だけを足し、H2の言い換え・H2の語の繰り返し（H2が選び方なのにH3が「〜で選ぶ」）にしない。他のH2ともH3とも、同じ事実を2箇所以上に書かない。**箱だけのH3（「料金」「送料」）は不可。** 書くべき別の事実が無いなら、H3は0本でよい（埋め合わせで書かない）。中身が2つしかない薄いH2は隣に統合するか消す。H2とH3を上から通して読むと結論がわかること。長さはH2・H3とも上限30字（FAQ質問H3は35字）。H3に「〜しよう」「〜ましょう」は使わない（まとめのH2だけ「まとめ：〜しよう」）。**例外＝結論型KW（やばい・やめとけ・危険・違法）だけは、H2にも答えを書いてよい**（outline.md に「見出し形式：結論型」の行を入れる）。**これから作る構成は、outline.md のメタ情報に「見出し形式：H2抽象」の行を入れる**（`lint-outline.sh` の `[H2が文]` `[H2が長い]` `[H3が長い]` が ERROR で止める。行が無い既存の構成は同じ検査が WARN のまま）。標準セクション（メリット/デメリット/選び方/注意点/よくある質問/まとめ等）は、これまでどおり標準語ラベルのまま。条件を二重に重ねた譲歩構文や、見出しへの自己言及（「〜という口コミは本当か」）は使わない（2026-08-07の学び9は、内容固有のH2も名詞句にすることで解消する）。
3. **具体性＝1つの事実を経済的に言い切ること。複数事実の列挙ではない。** 修飾語・数字は核の名詞に対し最小限（目安2つ）。1見出しで同時に満たそうとする要素は2つまで（優先順：結論＞平易さ＞KW）。埋めるための言い換え・冗長な動詞句（「〜を頼んだ」「〜で気をつけたい」）・曖昧名詞（定期/中身/目的等）を消す。専門用語・固有パッケージ名は見出しでは使わず平易な言葉に言い換える（本文中でのみカッコ補足可）。
4. **推測で数値・事実を書かない。** 裏取りできないものは書かず末尾免責へ（writing-manual §8）。
5. **景表法・信用毀損：有利な数字は同じ文に条件を書く。条件が書けないなら見出しに出さず本文・表に逃がす。** H2の金額は1つまで（範囲・複数併記は本文表へ）。ネガな評価は「〜という声もある」と口コミに帰属、ポジは言い切り。数量の主張（「〜と書く人が多い」）と口コミの擬人化はしない。
6. **口コミ見出しは実在口コミを収集してから確定する。** 収集前に「〜という声が多い」と決め打ちしない。一次ソースが取れなければ口コミH2を無理に作らず注意点H2に一本化する（捏造禁止）。
7. **カッコ・記号・疑問符は使わない**（FAQ質問H3の「〜ですか？」のみ例外。タイトルは？！可・年号不可）。**ただし区切りの `｜` は使ってよい**（「目的｜コース名」「まとめ｜〜」等。禁じたいのは見出しに補足を足して情報を詰め込むことであって、区切り記号そのものではない。公開記事で10箇所の使用実績あり・2026-09-09 Manabuさん指摘で解禁）。**FAQは4〜6問**、本文未回収のものだけ。
8. **提示前に、上記7項目を全見出しに1本ずつ当ててから出す。** 1点指摘されたら同じ型の欠陥を全見出しでgrepしてから直す（1つ直して再提示を繰り返さない）。着手前に同型記事（`articles/完成済み/`）のH3実物をgrepし、字数・語尾・主語を写経してから書く。**H2の粒度は写経しない**（旧形式のH2は結論の文が混ざる。2026-10-02）。
   - **1本ずつではなく「束」でも読む。** H2ごとにH3を縦に並べ、語尾・助詞・区切り記号が揃っていないか、同じ言い回しが3本以上続いていないかを見る。**1行ずつ見ると違反にならないが、5本並べて初めて分かる冗長がある**（2026-09-09「食のそよ風」で帰属表現が5本連続。lintの印字を読んで「音読チェック済み」と報告しながらH2しか見ていなかった）。これは `lint-outline.sh` のチェック14・15が機械で数える
   - **写経元の日付と、当てたい学びの日付を比べる。** 同型記事を写経すると、**古い実例が新しいルールを上書きする**。学びのほうが新しければ写経元より学びを優先する（2026-09-09、学び93「帰属表現を見出しで繰り返さない」が追加された当日に、それ以前の形式の記事を写経して同じ違反を作った）
   - **1点指摘されたら、直す前に同じ型を全見出しでgrepする。** 2026-09-09「食のそよ風」で5回往復したうち**4回は不要**だった。1箇所ずつ直して再提示を繰り返したのが原因（学び64）

10. **メインKWと共起語が見出しに入っているかを、競合比で採点してから提示する。** `scripts/check-kw-cooccurrence.py` を回し、**必須級の共起語（媒体3サイト以上が見出しで使う語）のカバー率80%以上**にする。80%は媒体で最上位のページの実測値を上回る水準として決めた。**60%未満はERROR**（媒体平均を割る）。メインKWの構成要素を含むH2が2本以下もERROR（学び93）。
   **ただし詰め込む道具ではない。** カバー率を上げる方法は2つだけ。①意味が良くなる形で見出しに入れる ②入れないなら outline の「共起語の配置計画」節に本文での置き場所か使わない理由を書く（書けば合格に数える）。**1見出しで満たすルールは2つまで**（🚨3・優先順は結論＞平易さ＞KW）。カバー率のために意味を壊したら本末転倒。

11. **語を入れ替えたら、提示前に3検査を通す**（2026-09-09 新設・auto-memory `midashi-jitsuzai-kensa`）。
   🚨10のカバー率を上げる作業は、**この3つを飛ばすと指摘の往復が延々と続く**。
   - **実在検査** — 見出しに使う名詞が、そのサービスに実在するものを指しているか。`service-info.md` と公式で1本ずつ確認する。**実在しないなら名詞で貼らず動詞形にする。** ✗「三ツ星ファームのお試しは冷凍庫の空きを先に確かめよう」（お試しという商品が存在しない）／✓「三ツ星ファームを試す前に冷凍庫の空きを確かめよう」。実在しない語は「実在しないので動詞形にした」と書けば 🚨10 の合格に数える
   - **入れ替え後の音読** — 語を差し替えたら、差し替えた**後**の文を声に出して読み直す。「音読チェック済み」と報告する前に、**変更した見出しだけを抜き出して**読む
   - **前提検査** — 実測値を目標にするときは、その実測が成立する前提が対象と同じかを確認する。**競合が持っていて自社ブランドに無い商品・機能の語は、カバー率のために貼ってはいけない。** 商品構成・訴求条件・記事タイプが違えば数値目標も違う
   > 2026-09-09の事故：KW出現率を公開6記事の93%に合わせようとして全H2に「お試し」を貼ったが、三ツ星ファームにお試しセットは存在せず、H2①で「ない」と書いた直後に存在しないものを主語にする論理破綻を起こした。**目標にした6記事は全社にお試し商品が実在していた。**

12. **競合が持っているからという理由だけで見出しを足さない。** `check-coverage.py` のERRORを消すことを目的にしない。
    出力に「過半が持つ＝必須／過半に届かない＝足す根拠は弱い」が印字されるので、過半に届かないトピックは
    **足す前に読者がそれを求めている証拠を確かめる**（①question-searchの質問に出るか ②自社の同型記事が持つか）。
    証拠が無ければ足さず、`outline.md` の網羅チェック節に数字つきで理由を書く。**理由を書くのは逃げではなく判断。**
    足した見出しは必ず `python3 scripts/check-appeal.py` に通す。**訴求社の指名記事で非訴求社の安さ・割引を書いたらERROR。**
    （2026-09-09 ニチレイ：他社比較H2を足したら、H3 3本中2本がナッシュの安さの宣伝になり「蛇足では？」と指摘された）

13. **主語がモノなら述語もモノに合わせる。** 「お試しセットは…頼む」のように主語がモノで述語が読者の行動になっていないか。
    可能形（頼める）にするか体言止めにする。`lint-outline.sh` チェック21が **ERROR** で検出する。

### 🔬 5レンズ検証（手順5・[verify-outline.js](verify-outline.js)）

**lint と Codex だけでは足りない。** 2026-08-04 に pipeline 14体・Codex・敵対検証3レンズを回して**文言品質の改善がゼロ**だった。原因は検査対象のズレで、全部が「ルール適合」「事実の正確さ」「論理構造」の検査であり、**「一読で意味が取れる日本語か」を見る工程が1つも無かった**（学び60）。

verify-outline.js は5本のレンズを並列で当て、**出た指摘を1件ずつ反証**させ、潰せなかったものだけを修正指示書にする。

| レンズ | 見るもの | 要点 |
|---|---|---|
| japanese | 一読で意味が取れるか | **ルールブックを渡さない。** 渡すとルール適合の検査に戻る |
| structure | article-structure の骨格 | ツリーと執筆メモの矛盾も見る |
| facts | 数値の整合・景表法 | 「使わない」と決めた数値の残骸を全件走査 |
| cannibal | 記事間の食い合い | **H3単位で突合。** check-cannibal は公開記事しか見ないため並走記事はここで見る |
| serp | 1位が取れるか | Ahrefsで**サブKWの検索数を実測**し取りこぼしを探す＋競合を実取得 |

**反証フェーズが効く。** 2026-08-05 の実走では、日本語レンズの誤指摘2件（「〜という声がある」をメタ記述と誤判定）を反証が正しく却下した。lint チェック7に「帰属表現は許容・ネガ見出しは帰属が必須」の除外規定があるため（学び59）。**指摘をそのまま採らず、反証の結論を見ること。**

⚠️ **Ahrefsの `keywords-explorer-overview` に渡す keywords はカンマ区切り。** 改行区切りだと空配列が返り、「データなし」と誤判定する（2026-08-05に実際に誤報告した）。空が返ったら、既知の大きいKWで同じ呼び出しを試してツールの正常性を切り分けてから結論を出す。

### Phase 1: モード判定（§4）
既存記事の有無＋順位資産で A リライト / B リポジショニング / C 新規 を判定。曖昧・順位取得不能なら聞き返す。

### Phase 2: SERP適合＋重複/カニバリ（§5.1G・§5.2）
- 実SERPの記事タイプ（比較/公式/EC/知恵袋/動画）を判定。狙うタイプが不一致なら構成を作る前に提起。
- 実データ＋SERP同一性でカニバリ判定 → 新規/既存強化/統合/棲み分けの決定木。棲み分け新規なら他社比較はスペック表を作らず向き不向きのみ・内部リンク誘導文も貼らない。
- **着手前に必ず Windsor→GSC で自サイトの既存ランクを確認**（指名/複合クエリで既にどのページが何位に出ているか）。**依頼が「新規」でも既存記事が拾っていればリライト/強化案件**（実例：2026-07「オイシックス お試し」は依頼上「新規」だったが、GSCで既存 #878 が pos3〜10 で存在＝リライト案件と判明。GSCなしでは重複記事を作るところだった）。

### Phase 3: 競合逆算で骨格を出す（§6.3・構成決定の本体）
上位10記事のH2/H3をクラスタリング → 必須トピック＋ギャップ。そこに依頼情報（訴求順位・掲載サービス）を最優先で重ねる。**型テンプレから生成しない。**

### Phase 4: 構成を組む（§6.1）
1. **記事の主役を1つ決める**（ペルソナの最大不安／検索意図の核）。
2. 読者の意思決定順（何がある?→どれ?→使うと?→注意→残る疑問→行動）に並べる。
3. 蛇足・水増しを削る（§5.1D・§7・§9）。
4. 単一サービスのレビュー/ガイド型は「選び方→サービス紹介〇選」テンプレを当てない（§6.3の勘所）。
5. 独自性（一次情報）枠を最低1つ確保（§6.4）。

### Phase 5: 品質ゲート（出力前に必ず1周）
- **論理関係ゲート（§9）**：各H2の"約束"を1文で言語化 → 全H3がその約束に答えるか → MECE・同粒度 → 崩れたら統合/分割/移動/削除で直す。
- **見出し文言（§8＋お手本）**：1H2=1トピック／意味不明なし／結論・平易／補足のカッコなし（区切りの `｜` は可）／タイトルの数値・訴求をH2で三重掲載しない。
- **音読チェック（2026-07-31 追加）**：タイトル・全見出しを一度音読し、数字と助詞のつながりが会話として成立するか確かめる（NG例：「手数料198円〜と1か月の食費を解説」）。硬語（試算・向き不向き等）は lint-outline.sh がERROR検出する。**実施結果は提示時に「音読チェック済み（書き直し◯件）」と1行報告する**（宣言なしのスキップを防ぐ）。
- **H2・H3にメインKWの構成要素＋共起語を左詰めで自然に**（全H2ベタ貼りの機械反復はせず自然分散・要件定義 §10.2）。**これは手順4dの `check-kw-cooccurrence.py` で機械採点する（カバー率80%以上）。目視で済ませない。****指名KW記事は例外＝結論型見出しを優先し、H2主語のブランド名反復を許容**（2026-07-02 Manabuさん裁定・§8-5）。
- **H2・H3に疑問符（？）を使わない**（「〜とは？」等の疑問符フックは平叙の名詞句に）。例外はFAQ質問H3の「〜ですか？」のみ（article-structure §6 よくある質問）。**タイトル（H1）は？・！を使ってよい**（口コミ・評判系の「〜は悪い？」等のフックは有効。2026-07-02 Manabuさん裁定）。
- **タイトル/メタ（§10.1）**：タイトルは？・！可（年号は不可）、メインKW左詰め、35〜45字。メタ120〜140字。URL英小文字ハイフン。サブKW2〜4。
- 差別化（上位を何で抜くか）・カニバリ棲み分け・依頼反映（ペルソナ/主要意図/PAA→FAQ/共起語/想定H2数）を再確認。

### 出力（§10）
`articles/{日本語KW}/outline.md` に：タイトル＋メタ＋URLスラッグ＋**見出し形式の行（`見出し形式：H2抽象`。結論型KWだけ `見出し形式：結論型`）**＋サブKW／各H2（約束1文付き）＋H3／FAQ（本文未回収のPAAのみ・語尾「〜ですか？」）／**情報台帳（`## 情報台帳`。2つ目の `---` より後ろ。要件定義§10.5c）**／カニバリ判定・差別化メモ。リライト時は操作タグ（※既存のまま／→変更／→新規／〔削除〕）と末尾に変更まとめ表。
- リサーチは `articles/{KW}/research.md` に保存する。
- **⚠️ 出力は「ファイル＋チャット要約」を必ずセットで。** リサーチ・構成・分析は、ファイル保存だけで終わらせず、**チャットにも一目でわかる要約（ボリューム・難易度・SERP上位・主要サジェスト・示唆）を必ず出す**。ファイルリンクだけで済ませない（§10）。
- **⚠️ 構成ができた時と、見出しを1本でもいじった時は、H2とH3を一文字も省略せずチャットに出す（2026-09-09 Manabuさん指示・省略禁止）。**
  - `bash scripts/show-outline.sh "articles/{KW}/outline.md"` を実行し、**その出力をそのまま貼る**。自分で書き写すと省略・言い換えが起きる
  - 出すタイミングは3つ。①構成案を作り終えたとき ②**見出しを1本でも直したとき**（1本の修正でも全体を出す） ③レビュー・検証の指摘を反映したとき
  - 「変更した箇所だけ」「主要なH2だけ」で済ませない。**毎回まるごと出す**
- **⚠️ 構成案のチャット表示は H1/H2/H3 の見出し階層だけで見やすく出す**（約束文・差別化/カニバリメモ・要裏取りは見出しツリーの後に分けて添える。構成本体は見出しだけで一目で追えるように）。
- **⚠️ 見出し・見出し行に（　）の注記を付けない**（「（主役）」「（約束：…）」等）。丸カッコ注記はチャットにもファイル見出し行にも付けず、主役/メモは丸カッコなしで別行に（例：★主役＝H2②）。見出し内カッコ禁止（§8-2）をチャット表示にも徹底。

## 第三者レビュー・鵜呑み禁止
- **構成v1を保存したら、Codexレビューを毎回・自動でバックグラウンド起動する**（2026-07-02 Manabuさん裁定：**構成レビュー用途の `codex exec` は常設許可**・都度のAskUserQuestion不要。`--sandbox read-only` は維持。構成以外の用途＝記事本文レビュー等は従来通り都度確認）。チャットへのv1提示と並行して走らせ、完了後に指摘の採否を1件ずつ判断する。
- **レビュー観点は3本立てに固定する（2026-08-04 改定）。** 従来は①だけを渡していたため、日本語の破綻と法務リスクを1件も拾えなかった。
  1. **このKWで検索1位が取れる構成か**（検索意図適合・必須トピック網羅・ギャップ独占・カニバリ・主役の尖り）
  2. **見出しの日本語が一読で通じるか**（意味不明・詰め込み・口コミの擬人化・そりゃそうだろの空見出し・H2とH3の論理整合）。**あわせて「タイトルが疑問形なら、H2①がその疑問への回答になっているか」を必ず判定させる**（学び70。2026-08-04にCodex自身の代替案も同じ欠陥を持っていたため、独立項目として明示する）
  3. **景表法と信用毀損のリスクがないか**（自社集計の数量を優良方向に使っていないか／訴求社の商品を断定で否定していないか）
  ※ 薬機法・健康増進法のレビューは従来どおり除外（別系統）。
- **Codexへの指示に、出力形式としてPASS/FAIL+issues形式を明記する（2026-08-09追加）。** 3観点それぞれについて `verdict: PASS/FAIL` と `issues: [...]`（該当箇所・欠陥の型・修正案）を出させる。自由文の講評だけだと採否判断に時間がかかり、同じ型の欠陥（学び58等）を見落としやすい。5レンズ検証のVERIFY_SCHEMAと同じ構造に揃える。
- **渡すファイルは絞る**：対象 outline.md・research.md・要件定義.md・internal-links.md・feedback_structure.md のみ。writing-manual／service-info の全文は渡さない（全ルール読み186kトークン・数分 → 大幅短縮）。
- **`Agent(subagent_type="codex-reviewer")` は使わない**（サブエージェントのBashがサンドボックスで動き `codex exec` が失敗し、レビュー捏造を誘発する既知バグ）。親ループが `.claude/agents/codex-reviewer.md` のStep3雛形で `codex exec` を直接実行する（auto-memory `codex-reviewer-fix.md` 参照）。
- 依頼を「確定」と言われても、ペルソナに刺さらない・蛇足・重複の懸念があれば AskUserQuestion で提起してから着手（§3.7）。

## モデル設定の目安
