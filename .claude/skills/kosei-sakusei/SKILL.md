# 構成作成スキル（kosei-sakusei）

**正本**：本ディレクトリの [要件定義.md](要件定義.md)（構成ロジック・品質基準の全定義）。本SKILL.mdは実行手順の入口で、詳細は §番号で 要件定義.md を参照する。実記事の傾向は [reference-yamadai-outlines.md](reference-yamadai-outlines.md)。
**大原則**：構成は固定テンプレ／型で決めない。毎回「競合上位の構成（§5.2・§6.3）＋依頼情報（KW・訴求順位・掲載サービス・その他指示）」で組む（§6）。過去記事の並びは参考実例であって固定ルールではない。
**🔧 三点同期**：見出し・出力ルールを改定したら、SKILL.md（🚨節・Phase 5）／要件定義.md／pipeline.js（RULES・FORMAT・プロンプト）の3点を必ず同時更新する（2026-07-02 レビューでドリフト検出：pipeline.jsに却下済みの「(約束: …)」形式と旧5項目RULESが残っていた）。

## 使うとき
- ヤマダイ（super-yamadai.co.jp/article）の新規/リライト記事の構成案を作るとき。
- 入力：**ターゲットKW ＋ 依頼情報（依頼シート）**。依頼情報がなくKWだけのときは Phase 0 で自動リサーチする。

## 🚨 絶対に守る（レビュー最頻の指摘・§7冒頭）
1. **1つのH2（配下H3まで含めて）で1トピック。** 「〜と〜」「〜や〜」で2トピックを並べない（要るなら別H2に割る）。
2. **一読で意味が取れない見出しを作らない。** 「980円の違い」等の圧縮語NG。何がどうなのか具体語で。
3. **競合の焼き直し・全部盛りにしない。** 記事の主役（ペルソナの最大不安／検索意図の核）を1つ決めて尖らせる。網羅は手段で目的ではない。
4. **見出しは結論・平易（中学生が一読）・カッコ/記号なし。** お手本（[references/gold-example-style.md](../../../references/gold-example-style.md)・[structure-examples.md](../../../references/structure-examples.md)）に文言を寄せる（丸パクリ禁止）。
5. **推測で数値・事実を書かない。** 裏取りできないものは書かず末尾免責へ（§F-4/§E-11）。
6. **H2・H3は答え・結論を書く**（目次だけで結論がわかる。箱だけの見出し＝「料金の目安」「中身と種類」等は全否認）。セクション名はSEO標準語（注意点/デメリット/メリット/選び方/口コミ/評判 等）を優先。FAQ質問H3のみ例外。
7. **FAQは4〜6問（できれば6問）。** 本文未回収のPAA・サジェストから。見出しツリーには質問文をH3として明記する（別セクション頼みで省略しない）。
8. **見出しに修飾語を詰め込まない（Manabuさん 2026-07-02）。** 地域＋対象読者＋運営主体＋カテゴリ等の複数属性を1見出しに全部乗せない。核の名詞に対し修飾語は2つまでに絞り、残りは本文・H3に譲る。**具体的（concrete）と冗長（verbose）は別軸**——具体性は核心を1つ経済的に言い切ることで、複数事実の列挙ではない。
9. **H2とH3で同じ話を繰り返さない。** H2が既に結論を言い切っている場合、配下H3はH2の言い換えではなく別の情報（実態・回避策・根拠等）を持たせる。
10. **隣接H2からの文脈が見えない唐突な見出しを作らない。** 前段のH2群で解消しきれない疑問を受けて次のH2があるなら、見出し自体（または導入文）にその橋渡しを入れる。
11. **「AとB」の対概念も1H2=1トピックの例外にしない。** 「向いている人と向いていない人」のような対も、良い/気になる口コミと同様に別H2に分ける。
12. **複数H2にまたがる同一事実は1箇所に一本化する。** 同じ事実（例：預け金の返金）を性質の異なる2つのH2に重複して書かない。
13. **見出しの冗長な動詞・連体修飾を削る（Manabuさん 2026-07-02）。** 「〜を頼んだ良い口コミ」「〜で気をつけたい注意点」「〜に関するよくある質問」等の動詞句・冗長修飾は削り「〜の良い口コミ」「〜の注意点」の最短形に。**異質な名詞を「と」で並列しない**（「中身と口コミ」＝野球とみかん。並列は同種要素のみ）。**単独で曖昧な名詞（定期／中身／目的等）は具体化**（定期→定期便）。
14. **「手順・流れ・方法」を掲げたH2のH3は実際のステップで揃える。** 支払い方法・仕様・スペックを手順に混ぜて論理を崩さない（「申し込み方法」H2に「支払い方法は〜」等のスペックH3を並べるのは論理崩壊。手順で統一するかセクション名を変える）。薄い2H3にせず読者が実際にたどる流れ（注文→支払い→到着等）で構成する。
15. **口コミ・評判系のH3見出しは実在口コミを収集してから確定する（プロセス順序）。** 実データがない段階で「〜という声が多い」等の見出しを先に作らない。気になる/悪い口コミの一次ソースが取れない場合は口コミH2を無理に作らず、弱みを事実ベースの注意点H2に一本化する（捏造回避・§A-7）。
16. **提示前に全見出しを1本ずつ🚨1〜15に当てる（最重要・rigor）。** 構造・カニバリのチェックだけで出さない。各H2/H3の日本語を「詰め込み・冗長修飾・異質並列・曖昧名詞・H2とH3の論理整合・セクションの役割が一目で分かるか」で1本ずつ推敲してから提示する。今回（らでぃっしゅ お試し）はこの逐一点検を飛ばしFBが多発した。

## 手順

### ⚡ 標準実行フロー（既定・2026-07-02 Manabuさん裁定）

構成依頼を受けたら**原則 [pipeline.js](pipeline.js) を `Workflow` で即起動する**。Phase 0〜5を本体ループで直列実行しない（らでぃっしゅ回で構成確定に時間がかかりすぎた反省。リサーチ3本・構成2案・検証3レンズが並列で走る）。依頼シートがあれば `args: {kw, request}` で必ず渡す。本体ループの仕事は次の6つだけ。

1. KW・依頼シートの受領確認（不足はここで聞く。以降は完走）
2. `Workflow({scriptPath: <pipeline.jsの絶対パス>, args})` を起動
3. 結果を `articles/{KW}/research.md`・`outline.md` に保存
4. **`bash scripts/lint-outline.sh "articles/{KW}/outline.md"` を実行し ERROR 0 まで修正**（見出しの機械チェック・数秒。カッコ/疑問符/冗長修飾/○つの/FAQ語尾＋カテゴリA硬語＝試算・向き不向き・シミュレーション等。タイトルにも適用）
5. **保存と同時にCodex構成レビューをバックグラウンド起動**（下記「第三者レビュー」節。毎回の確認は不要＝常設許可済み）
6. チャットに見出しツリー＋要約を提示（Codexが走っている間にManabuさんが読める）
7. Codex指摘の採否を1件ずつ判断して確定版に反映 → 再度 lint-outline.sh → 確定

下のPhase 0〜5は pipeline が内部で従う定義（＝正本）。本体で直列実行するのは「見出しの部分修正だけ頼まれた」「Workflow障害時」等の例外のみ。

### ⏱ 時間ルール（無駄撃ちの禁止・2026-07-02）

- **WebFetchのリトライは1回まで。** タイムアウトしたドメインは即 `https://r.jina.ai/{URL}` に切替え、以降そのセッション中は r.jina.ai 固定。**radishbo-ya.co.jp はタイムアウト常習のため最初から r.jina.ai を使う。**
- **Windsor GSC は定型で呼ぶ**：`get_fields` を呼ばない。`get_data`（connector=searchconsole・サイト `https://www.super-yamadai.co.jp/article/`・fields=query,page,clicks,impressions,position・直近3ヶ月・対象KWの部分一致）を直接叩く。結果はアンカー付きURL（#…）を除外し、クエリ×ページの上位20行に圧縮してから使う（生データを全量コンテキストに展開しない）。
- **既存記事の照合は `articles/公開記事一覧.md`（sitemap由来の全公開記事・`bash scripts/update-article-list.sh` で更新）＋GSC結果のURL＋internal-links.md だけ。** 一覧が7日以上古ければ先にスクリプトを回す。git log / git show / find でのリポジトリ考古学はしない。
- 公式ファクトの一次参照は service-info.md。公式サイトの最終裏取りは執筆段階に回す（構成段階は「要裏取り」リスト化で足りる）。**例外＝費用KW（料金/送料/値段/月額）は構成段階で実額まで裏取りする**（feedback_structure 学びS1）。

### Phase 0: 自動リサーチ（KWだけ渡されたとき・§2/§5.2）
ターゲットKWから依頼シートの各欄を可能な範囲で自動取得する。Ahrefs MCP は初回 `doc` で使い方を確認してから該当ツールを呼ぶ。取得できない欄は「未取得・要手動」と明示する（沈黙で埋めない・§2.5）。

| 依頼欄 | 取得元（MCPツール） |
|---|---|
| 検索ボリューム・難易度 | Ahrefs `keywords-explorer-overview` |
| サジェスト・複合KW | Ahrefs `keywords-explorer-search-suggestions` ＋ `keywords-explorer-matching-terms` |
| 関連KW | Ahrefs `keywords-explorer-related-terms` |
| 競合上位URL（SERP） | Ahrefs `serp-overview` → 上位URLを WebFetch して H2/H3 抽出・クラスタリング |
| 自サイトのカニバリ・順位 | **Windsor.ai `searchconsole` コネクタ**（**接続済み**・サイト `https://www.super-yamadai.co.jp/article/`。⏱時間ルールの定型 get_data で呼ぶ・get_fields禁止）＋ internal-links.md 照合。取得不能時は Ahrefs `site-explorer-organic-keywords`（自ドメイン）で代替 |
| 行動データ（ページ流入） | **Windsor.ai `googleanalytics4` コネクタ**（ヤマダイ接続済み・プロパティ 528283108 / 528278970。page_path×screen_page_views×sessions 等） |

- **自動取得しにくい欄はLLMで補完**（捏造禁止）：PAA（SERPのPeople Also Ask）／共起語（競合本文から頻出語抽出）／ペルソナ・ニーズ・知恵袋層（SERP＋一次情報の読み取りで仮説化し、断定しない）。
- 依頼シートが渡された場合は Phase 0 をスキップし、その内容を最優先で使う（数値・順位は1:1で扱い勝手に変えない）。

### Phase 1: モード判定（§4）
既存記事の有無＋順位資産で A リライト / B リポジショニング / C 新規 を判定。曖昧・順位取得不能なら聞き返す。

### Phase 2: SERP適合＋重複/カニバリ（§5.1G・§5.2）
- 実SERPの記事タイプ（比較/公式/EC/知恵袋/動画）を判定。狙うタイプが不一致なら構成を作る前に提起。
- 実データ＋SERP同一性でカニバリ判定 → 新規/既存強化/統合/棲み分けの決定木。棲み分け新規なら他社比較はスペック表を作らず向き不向きのみ・内部リンク誘導文も貼らない。
- **着手前に必ず Windsor→GSC で自サイトの既存ランクを確認**（指名/複合クエリで既にどのページが何位に出ているか）。**依頼が「新規」でも既存記事が拾っていればリライト/強化案件**（実例：2026-07「オイシックス お試し」は依頼上「新規」だったが、GSCで既存 #878 が pos3〜10 で存在＝リライト案件と判明。GSCなしでは重複記事を作るところだった）。

### Phase 3: 競合逆算で骨格を出す（§6.3・構成決定の本体）
上位10記事のH2/H3をクラスタリング → 必須トピック＋ギャップ。そこに依頼情報（訴求順位・掲載サービス）を最優先で重ねる。**型テンプレから生成しない。**

### Phase 4: 構成を組む（§6.1）
1. **記事の主役を1つ決める**（ペルソナの最大不安／検索意図の核）。
2. 読者の意思決定順（何がある?→どれ?→使うと?→注意→残る疑問→行動）に並べる。
3. 蛇足・水増しを削る（§5.1D・§7・§9）。
4. 単一サービスのレビュー/ガイド型は「選び方→サービス紹介〇選」テンプレを当てない（§6.3の勘所）。
5. 独自性（一次情報）枠を最低1つ確保（§6.4）。

### Phase 5: 品質ゲート（出力前に必ず1周）
- **論理関係ゲート（§9）**：各H2の"約束"を1文で言語化 → 全H3がその約束に答えるか → MECE・同粒度 → 崩れたら統合/分割/移動/削除で直す。
- **見出し文言（§8＋お手本）**：1H2=1トピック／意味不明なし／結論・平易／カッコ・記号なし／タイトルの数値・訴求をH2で三重掲載しない。
- **音読チェック（2026-07-31 追加）**：タイトル・全見出しを一度音読し、数字と助詞のつながりが会話として成立するか確かめる（NG例：「手数料198円〜と1か月の食費を解説」）。硬語（試算・向き不向き等）は lint-outline.sh がERROR検出する。**実施結果は提示時に「音読チェック済み（書き直し◯件）」と1行報告する**（宣言なしのスキップを防ぐ）。
- **H2・H3にメインKWの構成要素＋共起語を左詰めで自然に**（全H2ベタ貼りの機械反復はせず自然分散・§10.2／§F-1）。**指名KW記事は例外＝結論型見出しを優先し、H2主語のブランド名反復を許容**（2026-07-02 Manabuさん裁定・§8-5）。
- **H2・H3に疑問符（？）を使わない**（「〜とは？」等の疑問符フックは平叙の名詞句に）。例外はFAQ質問H3の「〜ですか？」のみ（§A-6）。**タイトル（H1）は？・！を使ってよい**（口コミ・評判系の「〜は悪い？」等のフックは有効。2026-07-02 Manabuさん裁定）。
- **タイトル/メタ（§10.1）**：タイトルは？・！可（年号は不可）、メインKW左詰め、35〜45字。メタ120〜140字。URL英小文字ハイフン。サブKW2〜4。
- 差別化（上位を何で抜くか）・カニバリ棲み分け・依頼反映（ペルソナ/主要意図/PAA→FAQ/共起語/想定H2数）を再確認。

### 出力（§10）
`articles/{日本語KW}/outline.md` に：タイトル＋メタ＋URLスラッグ＋サブKW／各H2（約束1文付き）＋H3／FAQ（本文未回収のPAAのみ・語尾「〜ですか？」）／カニバリ判定・差別化メモ。リライト時は操作タグ（※既存のまま／→変更／→新規／〔削除〕）と末尾に変更まとめ表。
- リサーチは `articles/{KW}/research.md` に保存する。
- **⚠️ 出力は「ファイル＋チャット要約」を必ずセットで。** リサーチ・構成・分析は、ファイル保存だけで終わらせず、**チャットにも一目でわかる要約（ボリューム・難易度・SERP上位・主要サジェスト・示唆）を必ず出す**。ファイルリンクだけで済ませない（§10）。
- **⚠️ 構成案のチャット表示は H1/H2/H3 の見出し階層だけで見やすく出す**（約束文・差別化/カニバリメモ・要裏取りは見出しツリーの後に分けて添える。構成本体は見出しだけで一目で追えるように）。
- **⚠️ 見出し・見出し行に（　）の注記を付けない**（「（主役）」「（約束：…）」等）。丸カッコ注記はチャットにもファイル見出し行にも付けず、主役/メモは丸カッコなしで別行に（例：★主役＝H2②）。見出し内カッコ禁止（§8-2）をチャット表示にも徹底。

## 第三者レビュー・鵜呑み禁止
- **構成v1を保存したら、Codexレビューを毎回・自動でバックグラウンド起動する**（2026-07-02 Manabuさん裁定：**構成レビュー用途の `codex exec` は常設許可**・都度のAskUserQuestion不要。`--sandbox read-only` は維持。構成以外の用途＝記事本文レビュー等は従来通り都度確認）。チャットへのv1提示と並行して走らせ、完了後に指摘の採否を1件ずつ判断する。
- **レビューのメイン観点＝「このKWで検索1位が取れる構成か」**（検索意図適合・必須トピック網羅・ギャップ独占・カニバリ・主役の尖り）。文言細部は従（2026-07-02 Manabuさん指定）。
- **渡すファイルは絞る**：対象 outline.md・research.md・要件定義.md・internal-links.md・feedback_structure.md のみ。writing-manual／service-info の全文は渡さない（全ルール読み186kトークン・数分 → 大幅短縮）。
- **`Agent(subagent_type="codex-reviewer")` は使わない**（サブエージェントのBashがサンドボックスで動き `codex exec` が失敗し、レビュー捏造を誘発する既知バグ）。親ループが `.claude/agents/codex-reviewer.md` のStep3雛形で `codex exec` を直接実行する（auto-memory `codex-reviewer-fix.md` 参照）。
- 依頼を「確定」と言われても、ペルソナに刺さらない・蛇足・重複の懸念があれば AskUserQuestion で提起してから着手（§3.7）。

## モデル設定の目安
- 生成・統合・最終化＝opus 高effort。機械的な整形＝低effort。
- **pipeline.js の起動が既定**（⚡標準実行フロー参照）。`Workflow({scriptPath: "<pipeline.jsの絶対パス>", args: "KW"})`、**依頼シートがある場合は `args: {kw: "KW", request: "依頼シート全文"}` で必ず渡す**（訴求順位・掲載サービス・ペルソナ・共起語を1:1で最優先反映）。リサーチにGSC既存ランク確認を含む。出力（research.md／outline.md 保存とチャット要約）とCodexレビュー起動・採否反映は本体ループが担当。
- **本文執筆も同様にpipeline化済み（2026-07-02）**：構成確定後は [write-pipeline.js](write-pipeline.js) を `Workflow({scriptPath: "<絶対パス>", args: "KW"})` で起動する（骨格→横断dedupe→文章化＋各自lint→4レンズ検証→修正→最終lintが並列実行される。CLAUDE.mdセッション2の直列手動フローの並列版）。完成後の意味レビュー（§E-12-b）・ゲート5（法令チェックリスト）・完成報告は本体ループが担当。
