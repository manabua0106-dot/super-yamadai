## 序章：読者像と書き手の声

このマニュアルの全てのルールは、以下の読者像と書き手の声を前提に作られている。

### 読者像（ペルソナ）

- **年齢・性別**：30〜60代の女性（主婦・共働き世帯）が中心
- **生活状況**：家事と仕事の両立で忙しい、または子育て中、またはシニアで料理の負担軽減を求めている
- **理解度の基準**：**中学生が読んで一発で理解できる文章**を書く

読者が読んで「難しい」「専門用語が多い」と感じたら、その文章は失敗している。

### 書き手の声（トーン）

- **フランク過ぎない**：「だよね〜」「〜だと思う！」のような距離感は NG
- **論文・学術調ほど固すぎない**：「〜であると考察される」のような硬さも NG
- **その中間**：丁寧だが上から目線にならない、信頼できる情報メディアのトーン

具体的な文末表現：「〜です」「〜ます」「〜できます」「〜してください」「〜しましょう」。「〜ですよね」「〜ますよね」は、導入の共感文など読者に寄り添う場面では使ってよい（多用は避ける）。

### ⭐ お手本文章（毎回参照）

文体・トンマナの基準は `references/gold-example-style.md`（お手本）を**執筆前に必ず読む**。実際にルールを守った文章がどう読めるかの生きた見本。**丸パクリは禁止**で、テーマに合わせて毎回書き起こす。ランキングパーツ・紹介順・数値は参考対象外（実データは service-info.md／公式が正）。

## 0. 執筆ワークフロー

═══════════════════════════════

記事は以下の工程順で進める。工程をスキップしない。

### 0-1. KW選定・検索意図の把握

1. メインKW（「食材宅配 一人暮らし」等）を決定する。
2. サジェスト・PAA（People Also Ask）・再検索KWを取得し、読者が知りたい情報を一覧化する。
3. 検索意図を「比較検討」「知識獲得」「購入直前」のどれかに分類し、記事の方向性を決める。

### 0-2. 競合リサーチ

1. メインKWで検索し、上位5〜10記事のH2/H3構成・掲載サービス数・独自コンテンツを表に整理する。
2. 上位記事が共通して扱っている要素を「必須要素」としてリスト化する。自社記事に抜け漏れがあってはならない。
3. 上位記事が扱っていない、または弱い要素を「差別化余地」としてリスト化する。
4. 差別化は「H3を無駄に増やす」のではなく、「既存H3の情報密度・具体性で上回る」方向で行う。読者のニーズから外れる冗長な追加はしない。
5. 上位記事の中で評価できる構成や表現はTTP（徹底的にパクる）し、自社記事に取り込む。

### 0-3. 構成案の作成

1. §A-1 の標準セクション構成に従い、H2/H3の見出しを仮決めする。
2. H3の見出しは以下の優先順位で決める：
   (a) 検索意図・サジェストから導かれる読者ニーズ
   (b) 競合の必須要素（上位5記事中3記事以上が扱っている項目）
   (c) 差別化要素（競合にない独自の切り口）
3. 掲載サービスの選定：訴求社を優先し、非訴求社はSEO網羅性のために追加する。
4. FAQのネタ出し：サジェスト・PAA・競合のFAQを確認し、本文で扱っていないニーズに限定する。

### 0-4. 執筆

推奨する執筆順序：

1. サービス紹介（テーブル → 紹介文 → CTA）
2. 選び方
3. メリット
4. 注意点
5. FAQ
6. 導入文（本文完成後に書いた方が内容と齟齬が出ない）
7. まとめ

#### 執筆時の出力ルール

- 改善後のHTMLは必ずコードブロック（```html）で出力する。
- 修正箇所を提示する際は、変更前→変更後を明示する。
- pタグは使わない。改行のみで段落を分ける。

### 0-5. セルフチェック → 納品

1. セクション単位で品質チェック（§G-4 のセクション完了チェックリスト）を行う。
2. 全文完成後に通しで読み、セクション間の重複・トーンの統一を確認する。
3. 競合比較チェック：上位3記事と構成を比較し、必須要素の抜け漏れがないか、情報が薄いH3がないか確認する。
4. 表現の出現回数チェックは推測でなく必ず検索（Ctrl+F）して正確にカウントする。
5. §G-5 の納品前チェックリスト（最終）を全項目確認する。

## A. 記事全体の構造

### A-1. 標準セクション構成

| # | セクション | 内容・ルール |
|---|---|---|
| 1 | 導入文（H2なし） | PASONA法で構成（§A-2参照）+ strongタグの行動促し文。H2は立てず本文のみ |
| 2 | 選び方（H2） | H2直下に導入1〜2文 + olリスト → H3×4〜5本 |
| 3 | サービス紹介（H2） | H2直下に導入文 + olリストで全社名一覧 → H3×各社（テーブル+FAB法紹介文+CTA） |
| 4 | メリット（H2） | H2直下に導入1〜2文 + olリスト → H3×3〜4本。各H3にstrong締め文（任意・§D-5／中身が薄ければ省略可） |
| 5 | 注意点（H2） | H2直下に導入1〜2文 + olリスト → H3×3〜4本。各H3にstrong締め文（任意・§D-5／中身が薄ければ省略可） |
| 6 | FAQ（H2）※任意 | H2直下に導入文 → H3×3〜4本。§A-6 参照 |
| 7 | まとめ（H2） | §A-5 参照 |

※ 記事テーマにより「料金相場」セクション（テーブル＋解説文、H3なし）や「〜とは？」セクションが追加される場合がある（§H 参照）。

### A-2. 導入文のルール（PASONA法）

導入文は **PASONA法** で構成する。

```
1文目（Problem）: メインKWを含む悩み提起
  型例：「〜は、＜読者メリット＞の食材宅配サービスです。」
  型例：「〜で迷っていませんか？」

2〜3文目（Agitation）: 放置リスクを示唆
  例：「比較せずに申し込むと割高なサービスを選んでしまう可能性があります」
  例：「自分に合わないサービスを選ぶと費用も手間もかかり続けます」

4文目（Solution）: 本記事の価値の予告
  形式：「この記事では〜を解説します」「この記事では〜を紹介します」で統一

末尾: <strong>タグの行動促し文（1文のみ）
```

#### 導入文ルール

1. 1文目にメインKWを必ず含める。
2. 読者の悩みを「〜あります。」「〜大変です。」「〜ですよね」などで共感する箇所を含める。
3. 末尾に `<strong>` タグで囲んだ行動促しの一文を入れる。
4. 導入文にH2は立てない。
5. 導入文で書いた内容を直後のH2セクションで繰り返さない。詳細はH2セクションに集約する。
6. 「本記事では」ではなく「この記事では」で統一する。
7. 「ぜひ参考にしてください」「参考になれば幸いです」等の定型フレーズは使わない（付録レイヤー5参照）。

### A-3. セクション導入パターン

各H2セクションの冒頭は以下の型に従う：

```
(a) 導入文2〜3文（セクション全体の要約。読者にとってのリスクや必要性を述べる）
(b) <ol> タグの番号付きリストで、直下のH3項目を一覧化（FAQ・まとめ除く）
(c) 各H3で個別解説
```

#### ルール

- olリストの各li要素とH3見出しのテキストは**完全一致**させる。
- H2直下の導入文は、単なる宣言（「〜を紹介します」）ではなく、読者にとってのリスクや必要性を述べる。
- **選び方・注意点の導入文** → リスク・必要性から入る。
- **メリットの導入文** → リスクではなくメリットの予告から入る（「宅配弁当に切り替えると〜が変わります」の型）。メリットセクションでリスクから入ると不自然。
- **サービス紹介の導入文** → 比較の必要性から入る。

#### NGパターン → 対処法

- 「10社のミールキットを紹介します」（宣言だけ） → 「ミールキットは各社で料金・配送エリア・メニュー内容が大きく異なります。比較せずに申し込むと割高なサービスを選んでしまう可能性があります。」（リスクを述べる）
- セクション導入文・まとめ文が記事間でほぼ同一 → テーマ固有の悩みや状況に触れる一文を必ず入れて差別化する

### A-4. 見出しルール

- H2: セクションの大見出し
- H3: セクション内の小見出し。**サービス紹介ではサービス名のみ（「1.」「2.」等のプレフィックスは付けない）**。代わりに `id="1a"〜id="12a"` の id属性を付与してジャンプリンクを実現する
- H4以下は原則使わない
- H1はWP側で管理（writerは使わない）

#### サービス紹介セクションの構造（必須）

H2②（サービス紹介〇選）直下には olリストではなく **3列比較表** を配置する：

```html
<table style="width: 100%;">
<tbody>
<tr><th>サービス名</th><th>1食あたり料金</th><th>特徴</th></tr>
<tr><td><a href="#1a">サービスA</a></td><td>約XXX円〜</td><td>短い特徴</td></tr>
<tr><td><a href="#2a">サービスB</a></td><td>...</td><td>...</td></tr>
...
</tbody>
</table>
```

各H3には `id="Na"` を付与（N=1〜12）：

```html
<h3 id="1a">サービスA</h3>
[サービスA_table]  ← _table登録済みなら
<strong>サービスAは、〜です。</strong>
...
```

※ コピペ時にH2タグが重複しないよう注意する。納品前に全H2タグの数を数えて確認する。

#### メインKW含有ルール

- **H2見出しにはメインKWの全構成要素を含める**（例：KW「宅配弁当 おすすめ」なら「宅配弁当」と「おすすめ」の両方）
- 複合KW（冷凍宅配弁当/一人暮らし/無添加等）をH3見出しレベルで入れる
- KWを見出しの左寄せに配置する
- 見出しを修正するたびにメインKWの含有を必ず再チェックする

### A-5. まとめセクションのルール

まとめセクションは以下の構成で書く。

1. `<strong>` タグの要約文（記事全体の結論を1〜2文で要約）
2. `<strong>` タグの行動促し文（具体的なアクション）
3. 短く締める。**3〜5文が目安**

#### ルール

- まとめH2の見出しは記事内の他のH2見出しと被らせない。特にH2②（サービス紹介）の見出しをそのまま繰り返さない
- 読者の次のアクションが見える見出しにする（「まとめ：おすすめの宅配弁当をお試しから始めよう」のように行動促しを含める）
- 「いかがでしたか」「参考になれば幸いです」等のAI定型で終わらない（付録レイヤー5参照）
- 本文の繰り返しにしない。新しい角度で要約する
- まとめ本文のstrong要約・strong行動促しは、具体的な行動に落とし込む
  - NG：「気になるサービスが見つかったら公式サイトを覗いてみてください」
  - OK：「送料込みの実質単価を比較し、お試しセットで味を確認してから申し込んでみてください」

### A-6. FAQセクションのルール

FAQセクションは以下の構成で書く。

1. H2 直下に導入文1〜2文
2. 各質問は H3 で立てる
3. 質問の語尾は **「〜ですか？」「〜ありますか？」「〜ますか？」で統一**する（丁寧語）
4. 回答は2〜3文で完結させる

#### ルール

- 本文で扱っていないユーザーニーズに限定する（**本文の焼き直し禁止**）
- サジェスト・PAA・競合のFAQから、本文で未対応のニーズを選ぶ
- 知恵袋への言及・引用は一切しない（§E-7b 参照）
- FAQ質問文に番号プレフィックス（「質問1：」「Q1：」等）を付けない
- **FAQのH2直下に質問一覧の `<ol>` を置かない**（2026-06-29 追記）。FAQは導入文1〜2文 → H3で各質問を直接展開する。olでの質問一覧は他セクション専用で、FAQ・まとめは対象外（§A-3 と連動）

#### NGパターン → 対処法

- 「〜か？」で終わる質問文 → 「〜ですか？」「〜ありますか？」「〜ますか？」に統一
- FAQ 回答で本文 H2〜H3 と同じ内容を繰り返す → 本文で未対応のニーズだけに絞る

### A-7. 口コミ・評判セクションのルール（blockquote形式・2026-06-22 追記）

お試し・レビュー系記事の口コミ・評判セクションは、以下の形式で統一する。

#### 構成（口コミ1件ごと）

```
[導入文] 何の口コミかを示す1文
<blockquote>口コミ本文（原文ママ・改変禁止）
<cite>投稿者の属性（確認できたものだけ）
出典確認元：<a href="URL" target="_blank" rel="nofollow noopener">サイト名</a></cite></blockquote>
[補足文] 読者向けに事実や対処を添える1文
```

#### 出典ルール（最重要）

- **同一KWで検索上位を占める競合のアフィリエイト記事・メディア記事は出典にしない**（自サイトから競合へ権威を渡さないため）
- 使ってよい出典：**中立の口コミ集約サイト（みん評・価格.com等）**、X・Instagram等の**一次投稿**、公式が公開するアンケート
- 引用元リンクには必ず `rel="nofollow noopener"` を付ける

#### 引用ルール（捏造防止）

- **実在の公開口コミのみをverbatim（原文ママ）で引用する。** 要約・言い換え・創作は禁止
- `<cite>` には確認できた属性だけを書く。**架空のハンドル名・年代・★評価を作らない**
- lint禁止語（「という」等）を含む口コミは使わない。マニュアルに沿った口コミを選ぶ
- 旧仕様・旧価格の口コミは、引用の直後に `※` で現行情報を注記する
- 良い口コミ・悪い口コミをバランスよく（同数程度）載せる

#### cite の属性表記（確認できたもののみ）

- X／Twitter：`— 投稿者名（@handle）YYYY年M月D日のXより` ＋ `出典確認元：<a ...>サイト名</a>`
- みん評・価格.com等：`性別／年代／利用商品／★評価`（記載があるものだけ）＋ `出典確認元：<a ...>サイト名</a>`
- Instagram：`Instagram投稿者：handle` ＋ `出典：<a ...>URL</a>`
- アンケート：`性別／年代／調査名`（公開済み属性だけ）
- 属性が分からないときは「みん評の投稿より」等と出典名だけ記し、属性は捏造しない

#### 取得手段の注意

- 役割分担：**口コミの「発見（どの投稿を載せるか）」は人が担当**し、構成・依頼に**X投稿の実URL**（`https://x.com/ユーザー名/status/数字ID` の1投稿1URL形式）を記載する。**「取得（原文・投稿者・日付の抜き出し）」はAIが担当**する。
- **構成・依頼にX口コミのURLがある場合、writerは必ずそのURLにアクセスして原文を取得し、blockquote＋cite形式で差し込む**（人手任せにしない）。手順は下記。
  1. URLからツイートIDを取り出し、`https://cdn.syndication.twimg.com/tweet-result?id={ID}&token=a&lang=ja` を WebFetch で取得する（Xの埋め込み用公開JSON。ログイン不要）
  2. 返ったJSONの本文(text)・表示名(name)・@ハンドル(screen_name)・投稿日時(created_at)を**原文ママ**で使う（要約・改変禁止）
  3. created_at（UTC）は日本時間（+9h）に直して `YYYY年M月D日のXより` と書く
  4. cite末尾に `出典確認元：<a href="{元のツイートURL}" target="_blank" rel="nofollow noopener">X</a>` を付ける
  5. lint禁止語（「という」等）を含むツイート、削除・鍵アカで取得できないツイートは使わない
- フォールバック：`publish.x.com/oembed` は有料化（402）で不可。みん評等の集約サイトは bot 拒否（403）で取得できないことがある。Xのハッシュタグページ直接アクセスも402で課金要求されることがある。**1回失敗しただけで「人が用意」に丸投げしない（死ぬ気で探す・2026-07-02追記）。** 諦める前に以下の迂回路を複数試す：
  1. **競合記事に埋め込まれたX投稿URLを辿る**：競合の口コミ記事をWebFetchし「埋め込まれているX/Twitter投稿のURLを列挙して」と指示すると、記事内に埋め込まれた実投稿のURLが取得できる。取得したツイートIDで上記の syndication CDN 手順を実行すれば原文が取れる（引用元は常に一次投稿URLであり競合記事自体は出典にしない＝§A-7の「競合記事を出典にしない」に抵触しない）。
  2. **サービス公式のアンケート・口コミ公開ページ**（例：`efriends.coopdeli.jp/look/life/questionnaire/` のような組合員アンケート公開ページ）を探す。「公式が公開するアンケート」は元々許可された出典（上記リスト参照）。
  3. **公式アプリのApp Store / Google Play レビュー**。サービス名で検索し公式アプリの配信ページをWebFetchすると、実名（ハンドル）・日付・レビュー本文が取得できることが多い。一次投稿の一種として扱う。
  4. それでも取れない場合のみ、捏造せず「取れた分だけ載せる／その旨を報告する」。
- **AIにできないのは「（Xの検索ボックスでの）ピンポイント発見」**であって、「探すこと」そのものではない。URL未特定（ハンドルのみ等）の口コミは、構成側で実URLまで特定しておくのが基本だが、上記1〜3の迂回路で自力発見できる場合は積極的に試す。Instagram は迂回路が乏しいため引き続き人が投稿URLを用意する。

#### 呼称ルール（ネガ語の和らげ）

- **「悪い口コミ」は使わず「気になる口コミ」と書く。** ネガティブな断定を避け、読者が中立に読める表現にする（見出し・本文・導入文すべて）。「良い口コミ」はそのまま使ってよい
  - NG：「悪い口コミをもとにデメリットを解説します」
  - OK：「気になる口コミをもとにデメリットを解説します」

#### H3見出し例

- 「良い口コミに多い意見」「気になる口コミに多い意見」、または「良い口コミ：〜との声が多い」「気になる口コミ：〜との声がある」

## B. サービス紹介セクションの書き方

═══════════════════════════════

### B-1. テーブル仕様（5行固定）

各サービスのH3直下に、以下5項目のテーブルを必ず配置する。**項目数は5行で固定**。

| 項目（th） | 内容・ルール |
|---|---|
| 会社 | 正式な運営会社名 |
| 費用 | お試し価格・定期価格・送料情報。税込表記を統一。記事テーマに関連する価格を優先記載 |
| 配送エリア | 全国 / 地域限定（具体的な都道府県名を列挙）。除外条件も必ず併記 |
| 配送日時の設定 | 指定可否、頻度、置き配対応の有無 |
| お試しの有無 / お試し内容 | 総合比較記事→「お試しの有無」、お試し特化記事→「お試し内容」。記事テーマに応じてth名を使い分ける |

#### テーブル共通ルール

- `<table style="width: 100%;">` を指定
- thのwidth: 25.8158%、tdのwidth: 74.1117%
- テーブル・画像・CTAは **`service-info.md` からコピペする**（自作禁止・外部ソースから補完禁止）

### B-2. 紹介文の構成（FAB法 + 訴求社strong価格訴求文）

サービス紹介のH3は以下の **FAB法 + ヤマダイ独自拡張** で構成する。

**⚠️ 紹介文の文数制約（2026-05改訂）**：紹介文は本文段落で **2〜4文** に抑える（strong段落含めて4〜6文）。「夫婦で1日1食」「平日5日分で〇食」など、無理やり夫婦の取り入れ方を追加する文章は禁止。読者が判断材料を得られれば十分で、利用シミュレーション文は不要。

```
段落1（Feature・特徴）: <strong>サービスの特徴を1つ（メインKW/複合KW含む）</strong>
  - 型例：「〜は、＜特徴＞の食材宅配サービスです。」
  - 特徴は1つに絞る。複数の情報を入れる場合は2文に分割する。1文に詰め込まない

段落2（Advantage・他社との違い・独自性）
  - 具体的に何が違うか
  - 比較対象を明示する
  - テーブルに記載した情報を本文で同じ角度・同じ数字で繰り返さない

段落3（Benefit・読者にとっての価値）
  - 機能の羅列ではなく、読者の生活・食卓での効果に変換する
  - 「カット済み食材で届く」→「包丁を使わずに10分で夕食が完成します」

段落4（訴求社のみ・strong価格訴求文）
  - 具体的な価格・割引情報があるときのみ <strong>価格訴求文</strong> をCTA直前に配置（任意。情報の薄い決まり文句は置かない）
  - 「〇〇%OFF」と書いた同一文内に適用条件を必ず併記
  - 非訴求社にはこの段落は入れない

段落5（任意・まとめの一文）

CTA（cta-templates.md からコピペ）
```

#### ルール

- 段落1のstrong 1文目には記事テーマのメインKWまたは「冷凍宅配弁当」等の複合KWを自然に含める
  - 冷蔵サービス（ワタミの宅食等）は「冷蔵の宅配弁当」でOK（「冷凍宅配弁当」は不要）
  - 「冷凍おかずセット」等、「宅配弁当」を含まない表現はNG
- **段落1の形式は「〇〇は、〜です。」のシンプルな主語＋述語に統一する**。「〇〇の最大の特徴は、〜である点です。」のような冗長な前置きはNG
- 段落1の特徴は1つに絞る（複数は2文に分割）
- 段落2〜3では、テーブルに記載した情報（料金・送料・エリア等）を本文で同じ角度で繰り返さない
- 段落4（訴求社のみ）：strong 価格訴求文 → CTA の順で配置
- 段落4は非訴求社には入れない
- 同じサービスが複数記事に登場する場合、記事テーマに合わせて切り口を変える

#### 紹介文に書いてはいけない蛇足パターン

以下のような「無理やり文章を増やす」パターンは禁止：

| NG | 理由 |
|---|---|
| 「二人で1日1食ずつ取り入れる場合、〇食分が必要なため平日5日で10食を目安に〜」 | 利用シミュレーションは読者がやればよい。記事は事実提示に徹する |
| 「夫婦で同じコースを選んで14食まとめ買いすると、配送頻度を月1〜2回に減らして時間の余裕を作れます」 | 行動の提案までは不要。事実提示で止める |
| 「冷凍庫スペースの確保がしやすい6食〜の小ロット注文に対応していて〜」 | 「小ロット注文」「対応」など業界用語的でわかりづらい |
| 「メニュー単位で個別に選んで注文する流れに対応しやすい設計です」 | 「流れに対応」「設計」が意味不明 |
| 「価格を抑えたいときはバリュー、おいしさを重視したいときはプレミアムと、用途に応じた使い分けができます」 | 自明な使い分けの説明は不要 |
| 「夫婦で別々の料理を選んで毎週入れ替えれば、平日の夕食メニューがマンネリになりにくくなります」 | 使い方の提案は不要 |
| 「コンビニ弁当や外食と比べて、カロリーや塩分を把握しながら食事を選べます」 | 比較は読者がやればよい |
| 「通常価格から28%OFFになる定期コースで、二人暮らしの食費を一定額に管理しやすくなります」 | 段落4のstrong価格訴求文と内容重複 |

#### 書き出しパターン（最低3種類を用意）

```
パターンA: 「サービス名は、＜特徴＞の冷凍宅配弁当です。」
パターンB: 「＜特徴＞を提供する〇〇は、」
パターンC: 「〇〇の最大の特徴は、〜です。」
パターンD: 「＜特徴＞を掲げる〇〇は、」
パターンE: 「〇〇は、＜特徴＞に特化した宅配弁当です。」
```

**15社の場合、同じパターンは最大5社まで。** 6社以上が同じ書き出しなら lint.sh で警告が出る。

#### NGパターン → 対処法

- 紹介文の構成・順序・表現が別記事とほぼ同一 → 段落の順番を入れ替え、書き出しを変える
- 「厳選した食材を全国に届ける食材宅配サービスです」等の汎用フレーズ → 記事テーマの切り口を冒頭に入れる
- サービス紹介文が機能の羅列だけ → Benefit段落で読者の生活効果に変換する
- 「お得に始められます」だけで、何と比較してお得なのか不明 → 「通常価格〇〇円のところ△△円で試せます」と具体的な比較を入れる
- テーブルのtd内容が全記事でコピペ同一 → 費用欄はその記事テーマに関連する価格情報を優先的に記載する

### B-2補足. 記事テーマ別の紹介文の切り口

| 記事テーマ | 段落1の切り口例 | 強調ポイント |
|---|---|---|
| 総合比較 | 「〜は、＜代表的な特徴＞の食材宅配サービスです。」 | サービス全体の特徴をバランスよく |
| お試しセット | 「〜のお試しセットは、＜価格・割引率＞で体験できる〜」 | お試し価格・内容・割引率・返金保証 |
| 離乳食 | 「〜の＜離乳食シリーズ名＞は、＜月齢対応＞の〜」 | 月齢対応・安全性・アレルギー配慮 |
| 安さ特化 | 「〜は、＜価格の安さ＞が魅力の食材宅配サービスです。」 | 1食あたり単価・送料無料条件 |
| 一人暮らし | 「〜は、＜一人暮らし向けの利点＞の食材宅配サービスです。」 | 少量注文・冷凍保存・配送柔軟性 |

### B-3. 掲載順のルール

- 掲載順は**依頼情報（構成書・発注指示書）の訴求順位**に従う（訴求順位は固定ではなく、記事ごとに変わる）
- 記載されているサービス名と順位番号をそのまま採用する
- 番号を勝手に連番に振り直さない。欠番・同率があっても依頼情報の通りに扱う
- H2②（サービス紹介）の掲載順は、訴求順位が最優先
- 訴求社を1番から順に配置し、非訴求社を後ろに回す
- 非訴求社の読者認知度（nosh・三ツ星ファーム等）を理由に先頭に置かない
- 依頼情報に訴求順位の記載がない場合は、`appeal-ranking.md`（カテゴリ別の基本ランキング）を使用する。該当カテゴリがなければ §C-4 のデフォルト訴求社を使う

## D. HTML / WordPress記法

═══════════════════════════════

### D-1. 見出しタグ

- H1は使わない（WP側で管理）
- H2: セクションの大見出し
- H3: セクション内の小見出し。サービス紹介では「1.サービス名」の形式で通し番号
- H4以下は原則使わない

### D-1補足. pタグ絶対禁止（最重要）

- **`<p>` `</p>` タグは記事内に1つも入れてはいけない。** writerは出力時にpタグを書かない
- 段落の区切りは「。」の直後に空行を入れる「一文一改行」で表現する（§E-3 参照）
- H2/H3直下の導入文も pタグで囲まない。改行のみで段落を分ける
- WordPress側で自動的にpタグが付与されるため、HTML側でpタグを書くと二重になり構造が壊れる
- lint.sh では現状検出されないため、writer/editor/style-checker が手動で確認する（執筆完了時に grep "<p>\|</p>" を実行して残数0を確認）

### D-2. 画像タグ

- H2直下への画像配置は**必須ではない**（記事タイプ・依頼情報に応じて配置）
- サービス紹介H3のみ、H3直下に画像を配置する
- 配置する場合のタグ構文：

```html
<img class="size-full wp-image-XXX aligncenter" src="https://www.super-yamadai.co.jp/article/wp-content/uploads/YYYY/MM/filename.jpg" alt="" width="800" height="XXX" />
```

- class: `size-full wp-image-XXX aligncenter`
- alt: 空文字（`alt=""`）で統一
- width: 800で固定
- 画像HTMLは **`service-info.md` からコピペ**（wp-image-XXX番号・パス・ファイル名・width/heightを1文字も変えない）

### D-3. リストタグ

- セクション冒頭の項目一覧：`<ol>` タグ（番号付きリスト）+ `<li>` タグ
- **本文中の箇条書き：使用してよい**（内容に応じて `<ul><li>` または `<ol><li>`）
- li 内の項目末には句点（。）を入れない
- ul/ol の直前に「何のリストか」を読者に伝える誘導1文を**必ず**入れる。唐突に箇条書きを始めない
- 誘導文のフレーズは記事内で分散させる。同じフレーズ（例：「〜をまとめました」）を3回以上使わない
- 誘導文の例：「確認しておきたい項目は次の通りです」「以下を参考にしてください」「次の点を意識してください」「〜の理由は下記の通りです」「〜の場合は以下の方法があります」

### D-4. テーブルタグ

- `<table style="width: 100%;">` を指定
- 左カラム: th（項目名）、右カラム: td（内容）
- thのwidth: 25.8158%、tdのwidth: 74.1117%
- サービス紹介テーブルは5行固定（§B-1 参照）

### D-5. strongタグ

`<strong>` タグの使用場面は以下の**5パターン**に限定する：

| # | 使用場面 | 補足 |
|---|---|---|
| (a) | 選び方・メリット・注意点セクションの各H3のstrong締め文 | H3末尾とは限らない。H3内の適切な位置に配置。新たな1文を足さず**既存の結論文**にstrongを付ける。本文で言い切れていれば省略可 |
| (b) | サービス紹介文の段落1の特徴キャッチ | 1文要約を太字化 |
| (c) | 訴求社のサービス紹介文のCTA直前の価格訴求文（段落4） | 非訴求社には使用しない |
| (d) | 価格・割引情報の強調 | |
| (e) | 導入文の末尾行動促し文 | |

#### ルール

- **1段落に `<strong>` が2箇所以上にならないようにする**
- strong締め文の直後に注記がある場合は、strongの外に `※` で分離する
- **情報ゼロのstrong締めは禁止**。「公式サイトで確認してから申し込めば安心です」「想定外の出費を避けられます」のような当たり前の文にstrongを付けない。strongは**具体的な数字・行動・サービス名**を含む文にだけ使う
- **strong締めのために新しい1文を足さない（最重要）**。strong締めは「H3内で最も重要な既存の文」に付けるもの。本文で結論を言い切れている場合は、その結論文にstrongを付ける。付けるべき既存文がなければ**strong締めを省略してよい**（埋めるための言い換え文の追加は禁止）
- **strong締めは本文のどの文とも内容が重複してはいけない**。1文目だけでなく、本文中段の文（2〜4文目）の言い換えになっていないか必ず確認する。重複していたら、その既存文にstrongを移すか、strong締めを削除する
- strong締めの候補: H3内で最も重要な「結論文（1文目）」か「具体的な価格・行動が入った文」にstrongを付ける

### D-5補足. サービス紹介文のstrong締め（価格訴求文）

訴求社のサービス紹介文の最終段落（CTA直前）には、具体的な価格・割引情報があるときのみ `<strong>` の価格訴求文を配置する（任意）。情報の薄い決まり文句は置かず、strongなしでCTAに直結してよい。

#### OK例

```
<strong>定期コースなら全コース28%OFF・送料無料で、最安のバランス栄養御膳は1食あたり約710円（税込）</strong>から始められます。
```

```
<strong>初回お試しセット（5食＋ごはん1食）が通常価格から47%OFFの3,218円（税込）</strong>で注文できます。
```

#### NG例

- 具体的な価格情報がないのに「割引価格で用意されています」等の情報の薄いstrongを無理に置く（訴求社でも置かず、strongなしでCTAに直結してよい）
- strongの中に価格情報がなく「おすすめです」「向いています」等の感想で終わる

### D-6. フォーマット整合性の注意点

#### NGパターン → 対処法

- H2直下にH3が1本しかないのにH3を立てている → H3が1本のみの場合はH3を立てず、H2直下にテーブルと本文を直接置く
- olリストの項目テキストとH3見出しテキストが不一致 → 完全一致させる
- サービス紹介テーブルの項目が4行や6行になっている → 必ず5行で統一
- まとめのH2見出しに「：」と「｜」が混在 → 記事内で記号は統一する（「：」で統一）
- CTAボタンの直前にキャッチコピー行がある社とない社が混在 → 訴求社は全社統一
- H2タグが重複している → コピペ時の貼り付けミスに注意。納品前に全H2タグの数を確認
- Post Snippetsのショートコードが別サービスのリンクに紐づいている → 使用前に管理画面でリンク先URLを確認

## E. 文章作法

═══════════════════════════════

### E-1. 文体・トーン

- **敬体（です・ます調）で統一する**
- 書き手の声は序章で定義した通り、「フランク過ぎず、論文調過ぎず、中間」
- 読者に語りかける口調を基本とし、「〜してみてください」「〜しましょう」を適度に使う。「〜ですよね」「〜ますよね」は共感文では使ってよい（多用は避ける）
- 過度にフランクにはせず、「信頼できる情報メディア」のトーンを維持する

### E-2. H3セクションのstrong締めパターン

選び方・メリット・注意点セクションのH3には、**H3内で最も重要な1文にstrongを付けて締める**（H3内の位置は最終段落に限らない）。strongは**既存の文に付ける**もので、締めるために新しい1文を足さない。本文で結論を言い切れていて付ける既存文がなければ、**strong締めは省略してよい**。

- 太字一文は「具体的な行動」または「読者にとっての価値」を述べる。抽象的な感想で終わらない
- **strong締めは本文のどの文とも内容が重複してはいけない**。1文目（PREP結論）だけでなく、中段の文（2〜4文目）の言い換えになっていないか必ず確認する
- 既存文と重複する締めしか書けない場合は、その既存文にstrongを移すか、strong締め自体を削除する（埋めるための言い換え文の追加は禁止）
- 1文目は「何ができるか」、strongは「読者にとっての価値」や「具体的な行動」で角度を変える

#### 合格例・NG例

```
OK：「公式サイトで郵便番号を入力すれば対象エリアかどうか調べられます。」
OK：「買い物にかかっていた時間を、自分の休息や趣味に使えるようになります。」
NG：「美味しさだけでなく、健康面でも安心できるのが大きな魅力です。」（感想止まり）
NG：「生活にゆとりが生まれます。」（抽象的）
```

#### strong締めのバリエーション（同じパターンは最大2回まで）

| パターン | 例 |
|---|---|
| 具体的な行動 | 公式サイトで郵便番号を入力すれば対象エリアかどうか調べられます |
| 読者の生活変化 | 買い物にかかっていた時間を自分の休息や趣味に使えるようになります |
| 失敗を避ける方法 | お試しセットで味を確認してから定期コースに申し込むと、合わない食事を避けられます |
| 数字で裏付け | まとめ買いしておけば急な残業の日もコンビニに寄らずに帰宅できます |
| 比較の判断基準 | 送料込みの総額を月単位で比べると、自分の予算に合うサービスが見つかります |

※ **strong締めの末尾に「〜を防げます」は使わない**（2026-06-29 追記）。「物足りなさを防げます」「失敗を防げます」のような定型は、具体的な行動・状態（「満足できます」「合わない食事を避けられます」等）に言い換える。本文中の具体的な「防げます」（例：「送料を計算すれば予算オーバーを防げます」）は対象外。
※ サービス紹介セクションのH3にはこのパターンではなく、D-5補足の価格訴求文で締める（訴求社のみ）。

### E-2補足. H3冒頭は結論から（PREP法）

選び方・メリット・注意点セクションの各H3は、以下の PREP構造 で書く。

```
[1文目] P: 結論（このH3の要点。メインKW/複合KWを含める）
[2文目] R: 根拠・理由（なぜそれが重要か）
[3〜4文目] E: 具体例（数値・固有名詞・条件を含めた具体的な内容）
[最終文] <strong>P: strong締め（具体的な行動 or 読者にとっての価値）</strong>
```

H3のボリュームは **4〜6文** を上限の目安にする（2026-06-29 改定：下限の縛りは撤廃。文数を満たすための埋め文は禁止。言うことがなければ短くてよい）。

#### NGパターン → 対処法

- 「食材宅配サービスは、会社ごとに特徴が大きく異なります。」（説明から開始） → 「お試しセットをいくつか試してみると、自分のニーズに合ったサービスを見つけやすくなります。」（結論から開始）
- 「赤ちゃんの成長に欠かせない栄養を〜」（背景から開始） → 「管理栄養士が献立設計に関与したメニューなら、月齢に応じた栄養を手軽に摂れます。」（結論から開始）
- 各H3の本文が見出しと無関係な内容を含む → 削除するか適切なH3に移動

### E-3. 文長・段落ルール

- **1文は60字以内**を目安とし、最長でも60字を超えないようにする
- **一文一改行**：文末の「。」の直後に必ず空行を入れる
- ただし ul/li 内は除く（li内は1項目1行）

#### 実装例

```
NG: 「食材宅配サービスの料金は各社で異なります。比較せずに申し込むと割高になる可能性があります。公式サイトで無料の資料請求ができます。」（3文が詰め込まれている）

OK:
「食材宅配サービスの料金は各社で異なります。

比較せずに申し込むと割高になる可能性があります。

公式サイトで無料の資料請求ができます。」（一文一改行で可読性向上）
```

### E-4. 体言止めの禁止

本文中の体言止め（「〜を実施。」「〜に対応。」）は使用しない。必ず「〜しています。」「〜です。」「〜できます。」で締める。

### E-5. 同じ表現の繰り返し回避

- 記事全体で同じ締め方や同じフレーズが3回以上出現しないようにする。執筆後にCtrl+Fで検索して確認する
- 連続する3文以上が同じ語尾（〜ます。〜ます。〜ます。）にならないようにする

#### NGパターン → 対処法

- 「〜で安心して利用できます」が5社連続で出現 → 「気軽に始められます」「不安なく利用できます」等バリエーションを出す
- 「〜が特徴です」が近い位置で3回以上 → 「〜に定評があります」「〜が魅力です」等に分散する
- 「忙しい方にもおすすめです」が記事内で3回以上 → 3回以上使っている表現を洗い出して言い換える
- サービス紹介の冒頭が全社同じ型 → 書き出しのパターンを最低3種類用意する
- H3末尾のstrong文が全セクション「〜してみてください。」で統一 → 「〜と安心です。」「〜と失敗しにくくなります。」等のバリエーションを混ぜる

### E-6. 比喩表現の禁止

物理的な意味と混同しうる比喩表現は使用しない。直接的な表現に置き換える。

- NG：「コストが跳ね上がる」→ OK：「費用が高くなる」
- NG：「食費がふくらむ」→ OK：「食費が予算を超えやすい」

詳細な禁止リストは **付録2：禁止語・NG表現リスト** のレイヤー3・9を参照。

### E-7. 内部リンク誘導文の禁止

「〇〇について詳しく知りたい方は『□□□□□□』も参考にしてみてください」等の内部リンク誘導文は使用しない。テーブル内のジャンプリンクのみ許可。

### E-7b. 外部情報源引用の禁止

Yahoo知恵袋・知恵袋・2ch・5ch 等のユーザー投稿型サイトへの言及・引用は一切しない。

#### NG例・OK例

- NG：「知恵袋では〜と言われています」「知恵袋でも〜」
- NG：「Yahoo知恵袋では〜という声がありました」
- OK：「〜と感じる人は多いです」など、引用せずに読者心理を代弁する
- OK：「〜と悩む方もいるでしょう」など、ユーザーの声を客観的に表現する

### E-8. 禁止語・制限語

#### 完全禁止（レイヤー1-a・ERROR）

| 禁止語 | 修正方法 |
|---|---|
| 体言止め（「〜を実施。」等） | 「〜しています。」「〜です。」「〜できます。」で締める |
| することができます | 「できます」 |
| 指示語（この / その / これ / それ / こうした / そうした） | 具体的な名詞に置き換える。例外は下記のみ |
| 無責任系語尾（〜とされています / 〜ようです / 案内されています / 〜とのこと / 〜と思われます / 〜と見られます） | 事実は言い切る。裏取りできないなら書かない |
| 見出し（H2/H3）内の（） | 見出しに補足の（）を入れない（本文の nosh（ナッシュ）等はOK） |

> 2026-06-29 再改定：指示語は「やっぱり禁止」に戻した（ライフミール記事で「この特別価格」「その後は」が頻発し読みにくくなったため）。完全禁止に伴う不自然さは、下記の例外＋「口コミ（blockquote）内は検査対象外」で回避する。

#### 努力義務（レイヤー1-b・2026-06-29 緩和・lintはWARNING）

下記は**禁止ではない**。文脈で自然なら使ってよいが、**極力、具体的な名詞・動詞に置き換える努力をする**。
「という/として」を完全禁止にすると不自然な代替（「との」等）を誘発し、文章が固く・空っぽになるため緩和に留める。

| 語 | できれば |
|---|---|
| として | 具体的な表現に（自然なら可） |
| という / といった | 直接記述／「〜や〜など」に（自然なら可） |
| 強調用の「」（会話・固有名詞・口コミ以外） | 強調目的の「」は使わない（lintはWARNING・誤検出しやすいため一読で判断） |

#### 指示語の例外（許容）

- 「この記事では」→ OK
- 「この口コミのように」「この口コミの方は」→ OK（直前の引用を指す）
- 「そのまま」「そのもの」→ OK／「そのため」→ OK（接続詞）／「それぞれ」→ OK
- **口コミ（blockquote）内は対象外**（原文ママのため改変しない）

#### ⚠️ 2026-04 改訂で除外

以下は過去に完全禁止だったが、v4.0 から**使用OK**：

- **こと**（名詞化）→ 自然な日本語として必要な場面がある
- **〜しましょう / 確認しましょう** → 通常文の行動喚起として OK

#### 制限あり

| 表現 | ルール |
|---|---|
| 「〜い。」で終わるアドバイス文 | 「〜です。」「〜できます。」「〜してください。」で締める。「〜いです。」はOK |
| 「」（カギ括弧） | 会話文・固有名詞・読者心理描写のみ。強調目的では使わない |

詳細な禁止語リストは **付録2：禁止語・NG表現リスト** を参照（レイヤー1〜14 + ヤマダイ固有カテゴリ）。

### E-9. 読者視点の担保

すべての記述が「読者にとって何の役に立つか」を意識する。

#### 専門用語の補足説明（汎用ルール）

- **業界用語の初出時**：カッコで補足（例：「独自の安全基準『RADIX基準』（農薬・添加物の使用制限ルール）」）
- **業界の正式名称にこだわらず、読者に伝わる言葉を優先する**（例：「出資金」→「預け金」）
- **食材・調理用語の初出時**：平易な言葉で補足（例：「ミールキット（食材とレシピがセットになった調理キット）」）
- **制度名の初出時**：説明を付ける

#### その他の読者視点ルール

- サービス紹介文が機能の羅列だけにならないようにする（「カット済み食材で届く」→「包丁を使わずに10分で夕食が完成します」のように読者の生活での効果に変換する）
- 「〜を確認しましょう」だけで終わらない。具体的な方法を添える
- 「お得に始められます」だけで終わらない。何と比較してお得なのかを明示する
- strong締めは直前の本文から自然に導ける内容にする。本文で述べていない論理に飛ばない
- 主語が省略されて何の話か分からない文を避ける
- **状態は読者目線（受け取る側）で描写する。** 口コミ・レビュー記事は「読者が実際に受け取って体験する側」なので、サービスの仕様を説明する送り手目線の「〜します／入ります」より、すでにそうなっている状態を見せる受け手目線の「〜ています／届きます／入っています」を使う（§B-2「届ける→届けてくれる」と同じ考え方）
  - NG：「季節ごとに違う野菜が入ります」（仕様説明・送り手目線）
  - OK：「季節ごとに違う野菜が入っています」（受け取った箱の状態・読者目線）

### E-10. つながりのある段落構成

2文を並べただけの段落を避ける。前の文と次の文が論理的につながっているか確認する。

- NG：「全国配送に対応しています。配送日時の指定も可能です。」（関連が弱い）
- OK：「全国配送に対応しており、配送日時も指定できるため、ライフスタイルに合わせて利用しやすいサービスです。」

#### 接続詞で文の関係を示す（一文一改行でも「ぶつ切り」にしない）

一文一改行（§E-3）でも、文をただ「。」で切って並べるだけにしない。**隣り合う文の関係を接続詞で示し、PREP（結論→理由→具体→対策）の流れがわかるようにする。**

- 役割の接続詞を使う：理由は「〜からです」、順接は「そのため」、逆接は「ただし」「それでも」、追加は「さらに」「また」
- 各文がPREPのどの役割か（結論／理由／具体／逆接／対策）を確認し、役割が飛んでいたら接続詞で橋渡しする
- 「文がただ羅列されていて流れがない」と感じたら、文の順序をPREP順に直し、つなぎ言葉を入れる

```
NG（ぶつ切り・関係が見えない）:
自分で野菜の種類を選ぶことはできません。
苦手な野菜が入ったり、使いたい野菜が届かなかったりする場合があります。
献立を決めてから買い物をしたい方には、不便に感じる場面があります。

OK（接続詞で関係を示す）:
坂ノ途中では、自分で野菜の種類を選べません。
旬においしい野菜を詰め合わせた「おまかせ」で届くからです。
そのため、苦手な野菜が入ったり、使いたい野菜が届かなかったりする場合があります。
それでも、届いた野菜で料理を工夫する楽しみを大切にしたい方には向いています。
```

### E-11. 「（公式サイトで要確認）」等のミニ免責は本文で繰り返さない（2026-06-22 追記）

- 本文中に「（公式サイトで要確認）」「（時期により変動）」「（適用条件は〜）」等のミニ免責・要確認文を**繰り返し入れない**
- 価格時点・条件・最新情報の確認喚起は、**記事末尾の免責ブロック1箇所に集約**する
- 出典リンク（例：`（[〇〇公式](URL)）`）も本文に散らさない。数値の裏取りは執筆時に行い、本文はすっきりさせる
- **景表法（有利誤認）の担保**：`%OFF`・`送料無料`・`初回割引`・`返金保証`・`最大〇〇` 等を使う場合は、記事末尾の免責ブロックに「割引・送料・特典・返金の適用条件は各公式サイトで要確認」を必ず1文入れる（これがインライン条件併記の代替になる）
- 本ルールは §G-5・付録1 の「インライン条件併記／導入strong直後の注記」より優先し、免責は末尾集約とする
- lint.sh は `送料無料`・`%OFF` 行で WARNING を出すが、末尾免責で担保していれば ERROR ではないため許容する

### E-12. 執筆時の自己検算と提示前の意味レビュー（2026-06-29 追記・最重要）

lint（grep）は文字列しか見ない。**意味が空・重複・薄い・不自然**は機械では拾えない。writer はこれを「書く瞬間」と「提示前」の2段階で自分で潰す。

#### 12-a. 1文ごとの自己検算（書く瞬間に毎文かける）

1文を書いたら、出力する前に次の4つを通す。1つでも引っかかったら直す。

1. **この文を消しても意味が変わらないなら消す。**（「〜が魅力です」「〜が大切です」「〜が重要です」など、体裁を埋めるだけの文を撲滅）。**読めば誰でもわかる当たり前の総括（「品揃えは3社の大きな違いです」「料金は各社で違います」等）も書かない**。代わりに何がどう違うかを具体名で書く
2. **主語と述語が具体名詞・具体動詞か。**（「味と便利さ」「目的」「タイプ別」「生活の質」など抽象語で止めない。何がどうなるか具体で書く）
3. **中学生が読んで一発で像が浮かぶか。**（「実質」「圧迫」「占有」「プラン料金」など業界語・硬語を排除）
4. **前のH2/H3で同じことを言っていないか。**（重複・薄さ。言うことがなければ短くする＝埋め文より空白がマシ）

#### 12-b. ユーザー提示前の意味レビュー（必ず1周）

**lint ERROR 0 は「提示してよい」の合図ではない。** 記事・セクションをユーザーや次工程に渡す前に、通しで一読して以下だけを見る。

- 抽象的で意味不明な文（12-a の2に該当）
- 同じ話の繰り返し（セクション間の重複）
- 内容が薄いH3・空のstrong締め
- 硬い言い回し・不自然な代替（「との」連発など）

迷う規模・重要記事はCodex第三者レビューを通してから提示する。**`Agent(subagent_type="codex-reviewer")` は使わない**（サブエージェントのBashがサンドボックスで動き `codex exec` が失敗しレビュー捏造を誘発する既知の恒久バグ）。**親ループが、そのつどユーザーに確認のうえサンドボックス制限解除の許可を得てから** `codex exec` を実行する（詳細は `.claude/agents/codex-reviewer.md` のStep3雛形・auto-memory `codex-reviewer-fix.md` 参照）。

> このルールは「lint通過＝OK」という誤った安心を禁じるためのもの。**機械チェックは必要条件、意味レビューは十分条件**。両方通って初めて提示できる。文体の見本は `references/gold-example-style.md`（お手本）を毎回参照する。

## F. SEO

═══════════════════════════════

### F-1. メインKWの配置

メインKWを以下の箇所に自然に含める：

(a) 導入文の1文目（必須）
(b) 各H2見出し（メインKWの**全構成要素**を含める）
(c) 全サービスの紹介本文に最低1回
(d) まとめセクションのH2見出しと本文
(e) メリット・注意点のH3本文の1〜2文目に記事テーマのメインKWまたは複合KWを含める
(f) サブKWはH3タイトルにも自然に含める

※ 同じサービス名が記事内で過度に出現しないようにする（SEOスパム防止）。

### F-2. サブKWの活用

記事テーマに応じたサブKWを各H3の本文に分散させる。不自然な詰め込みは避ける。

### F-3. 共起語の網羅

記事テーマの共起語を本文に自然に含める。共起語は執筆前のリサーチ段階で一覧化し、`articles/{KW}/cooccurrence-plan.md` として配置計画を作成する（ゲート1）。

### F-4. 出典URL併記ルール

具体的な数値・統計を本文に書く場合、`[出典名](URL)` 形式でリンクを併記する。

#### ルール

- 枕詞（「公式サイトによると」「〜のデータでは」等）は不要
- 数値と出典リンクを併記するだけでよい
- 出典を確認できない数値は記載しない
- 加工・推計した数字を出典付きで書かない

#### 実装例

```
NG：「公式サイトによると、累計注文数は100万食を超えています。」
OK：「累計注文数は100万食を超えています（[Oisix公式](https://...)）。」

NG：「調査によれば、利用者の8割が継続しています。」
OK：「利用者の8割が継続しています（[〇〇社2025年調査](https://...)）。」
```

### F-5. タイトル・ディスクリプションのルール

- タイトルに年号（【20XX年】等）は使わない。メインKWをタイトルの最左に配置する（2026-06 改定）
- KWを詰め込むあまり日本語として不自然にならないか必ず確認する
- タイトル・ディスクリプションで造語や意味不明な複合語を使わない

## G. 品質管理・チェックリスト

═══════════════════════════════

### G-1. 事実確認

すべての記述は公式サイトで事実確認できるものに限る。確認できない情報は書かない。

- 出典を記載する場合は、URL単位で裏取りできるデータのみ使用する
- 加工・推計した数字を出典付きで書かない
- 景表法・薬機法・健康増進法に抵触する表現がないか確認する（**付録1：法令セーフ変換表** を適用）
- 数値には `[出典名](URL)` を併記（§F-4）

### G-2. 記事間の重複防止

同じサービスが複数記事に登場する場合、紹介文の構成・表現を記事ごとに変える。3文以上同一の箇所がないかチェック。

### G-3. 記事内のセクション間重複防止

選び方・メリット・注意点・FAQ・目的別の各セクションで、同じ内容を同じ角度で書かないようにする。

#### NGパターン → 対処法

- 選び方H3とメリットH3で同じテーマを同じ角度で扱っている → 選び方は「比較の方法」、メリットは「読者にとっての効果」と角度を分ける
- 選び方H3と注意点H3で同じ内容を書いている → 選び方は「判断基準」、注意点は「失敗パターンと対策」と角度を変える
- FAQが本文の既出内容の焼き直し → FAQは本文で扱っていないユーザーニーズに限定する
- strong締めが本文の文（1文目・中段の文いずれも）とほぼ同じ内容 → 言い換えで埋めず、既存の結論文にstrongを移すか締め文を削除する
- 目的別セクションでサービスに触れる場合、紹介セクションと同じ情報で繰り返さない

### G-4. セクション完了チェックリスト（H2ごとに実行・ゲート3b）

## I. 訴求設計のルール

## J. 競合分析・差別化

═══════════════════════════════

### J-1. 差別化の方向性

## L. 5グループ責任分担

═══════════════════════════════

ヤマダイ記事制作の10エージェントは、責任の性質で5グループに分かれる。

### 🟪 グループA：企画系（researcher）

構成案作成・SERP分析・競合TTP・ペルソナ設計を担当。
記事の「設計図」を作り、writerに引き渡す。

### 🟦 グループB：執筆系（writer）

本文執筆（骨格→文章化の2段階）を担当。
writerは以下の絶対遵守事項を守る：
- H2単位で執筆する（一気書き禁止）
- `service-info.md` からコピペする（テーブル・画像・CTA）
- pタグは使わない
- 一文一改行・60字以内
- 推測で数値を書かない（`[出典名](URL)` 併記）
- 書いたら自分でチェックして、問題があれば自分で直してから出力する

### 🟫 グループC：統率系（editor）

チェッカー4体の指摘を統合し、writerへの修正指示を1つにまとめる。
強制ゲート5つの門番として、チェックポイントファイルの存在を確認する。

#### 矛盾解決の優先順位

チェッカー間で矛盾が起きた場合、以下の優先順位で解決する：

| 順位 | チェッカー | 理由 |
|---|---|---|
| 1 | duplicate-checker | 重複は読者体験を直接損なう |
| 2 | prep-logic-checker | 論理破綻は信頼を損なう |
| 3 | iron-rule-checker | 読者に伝わらない表現は離脱の原因 |
| 4 | kw-checker | SEOは重要だが読者体験の後 |

### 🟩 グループD：自動検査系（quality-checker / style-checker / kw-checker）

文字列 grep や構造的ルールで検出可能なチェックを担当。
lint.sh と連携して自動検査を行う。

### 🟥 グループE：意味検査系（editorial-reviewer / iron-rule-checker / prep-logic-checker / duplicate-checker）

LLM-based の意味検査が必要なチェックを担当。
文脈判断・意味上の重複・論理整合性・読者視点など、単純 grep では検出不可な項目を扱う。

#### カテゴリB：後述系禁止

#### カテゴリE：過去事故ログ（同じ間違いを繰り返さない）

- 「8週間で120種類のメニューが届く」→ 根拠なし。「メニューは定期的に入れ替わるため、同じ料理が続きにくい」に修正
- 「お試し8食6,307円」→ 公式サイトで確認不可。「お試しセットあり（内容は時期により異なる・公式で要確認）」に修正
- 「送料990円（地域別）」→ 正しくは「送料990円〜（食数別）」。送料の計算方法を正確に確認する
- 「医師が献立を監修」→ 過誇張。「専門医の指導のもと管理栄養士が献立を監修」に修正
- 価格改定の見落とし多発 → **service-info.mdの価格のみを使う。記憶や外部ソースから補完しない**

#### カテゴリF：制限あり

| 表現 | ルール |
|---|---|
| 「〜い。」で終わるアドバイス文 | 「〜です。」「〜できます。」「〜してください。」で締める。「〜いです。」はOK |
| 「」（カギ括弧） | 会話文・固有名詞・読者心理描写のみ。強調目的では使わない |
| おすすめです | 記事内3回以内 |
| 根拠のない具体数字 | 出典URLで裏取りできない数字は使用禁止 |
| 「〜とされています」「一般的に〜」 | 裏取りできないなら書かない（逃げない） |
